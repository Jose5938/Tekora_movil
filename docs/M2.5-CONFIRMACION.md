# M2.5 · Confirmación B2

Se apila sobre M2.4 y consume la lectura M2.1 de Laravel `a21802f0917132919b0be34087fee03236de2dc0`. [Readiness M2.1](https://github.com/Fernando261/tekora-project/blob/a21802f0917132919b0be34087fee03236de2dc0/docs/api/M2.1-MOBILE-CONFIRMATION.md).

El seguimiento y el detalle de reserva muestran los estados observados de `confirmation_readiness`. El botón solo se ofrece para el protocolo B2 con ambas lecturas en `ready` y `can_offer_mobile_confirmation=true`, ID y versión de reserva coincidentes, hold vigente con su propia versión y plazo local positivo. En el acto de confirmar se reconsulta checkout-context y se comprueba que el plazo local no haya vencido. Lecturas ausentes, incoherentes, bloqueadas o desconocidas cierran la acción.

Confirmar requiere un acto explícito. Se envía `PATCH /reservations/{id}/commit` con la versión de la reserva y UUID asociado a esa intención. Tras incertidumbre se reconsulta el estado y se conserva la clave para una repetición explícita del mismo comando. Se muestra confirmación únicamente para una respuesta `confirmed`. La app no inicia pagos, visita B3.2 ni construye un checkout.

Linux: `npm ci` salió 0 con 807 paquetes. Node 22.13.0 y 24.22.1 pasaron 60/60 cada uno. TypeScript, lint y `git diff --check` salieron 0. Se validaron cuatro fixtures readiness contra OpenAPI. La exportación web produjo 15 rutas y Chromium pasó 16 grupos sin errores de página. La prueba comprueba que el estado con requisito web no ofrece commit y que dos intentos explícitos tras 503 conservan la clave y la versión de reserva.
