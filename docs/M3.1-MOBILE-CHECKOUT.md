# M3.1 — Checkout ficticio integrado en Tekora Móvil

La app ahora usa un checkout visual Tekora en lugar de una pantalla PayPal provisional. Se conecta al PR [Laravel #58](https://github.com/Fernando261/tekora-project/pull/58), no a la web HTML ni a un proveedor de pagos.

## Contrato V8.1.10

Para una reserva marcada con `simulated_checkout.required`, la app consulta y registra la selección con `GET/POST /reservations/{id}/checkout`. Configura la URL mediante `EXPO_PUBLIC_API_BASE_URL=https://api.tekora.mx/api/v1`. Tarjeta envía `method: "card"`, `instrument: "tekora-test-card"` y el UUID. Efectivo envía `method: "cash"` y el UUID. Los campos visuales de tarjeta son de solo lectura.

La app conserva el UUID ante una respuesta incierta y obtiene el resultado persistido por GET. La selección deja la reserva retenida y la confirmación B2 se solicita explícitamente desde la ficha. La retención original dura 900 segundos. [OpenAPI V8.1.10](https://github.com/Fernando261/tekora-project/blob/111835c2003e6597150f2ef2be231e5c51bc466d/docs/api/openapi.json)

## Laboratorio B3.2

La ruta histórica `demo-checkout` está disponible en el laboratorio SQLite desechable B3.2: servidor local `http://127.0.0.1:8097`, sin .env y con marcador privado del generador. En `C:\xampp\htdocs\TEKORA\database\database.sqlite` devuelve 404 por seguridad. No crear marcadores ni tablas sintéticas a mano.

1. Clonar Laravel en carpeta independiente, cambiar a rama `codex/m31-mobile-demo-checkout-api`, preparar dependencias y ejecutar verificador/lanzador en `docs/payments/B3.2-INTEGRATED-LOCAL.md` del backend.
2. Cambiar a rama `codex/m31-tekora-mobile-checkout-ui` del repositorio móvil. Conservar una copia local de la configuración anterior y poner en `.env.local` (solo Expo Web en la misma PC):

   ```dotenv
   EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:8097/api/v1
   EXPO_PUBLIC_ALLOW_LOCAL_HTTP=1
   EXPO_PUBLIC_ENABLE_LOCAL_DEMO_CHECKOUT=1
   ```

3. Usar el cliente temporal impreso por el lanzador B3.2. La reserva retenida inicial exige pago de prueba; el enlace «Elegir método de pago de prueba» aparece en su ficha.
4. Elegir tarjeta ficticia o efectivo. La aprobación de prueba y el efectivo pendiente habilitan la posterior confirmación de la reserva. Volver a la reserva: el estado se refresca y el comando B2 sigue independiente.
5. Si expiran los 900 segundos, crear una fixture nueva con el lanzador. Jamás prolongar un hold cambiando el reloj o la base.

## Criterios de seguridad

El módulo no procesa dinero. Los tres números, el vencimiento 12/30 y el CVV 123 son **exclusivamente valores ficticios permitidos en el laboratorio**; no se admiten tarjetas personales. La UI no guarda PAN/CVV. Las credenciales reales o bases existentes no se copian al laboratorio. `awaiting_cash` no significa dinero recibido. Backend verifica el cliente propietario, cotización, estado, idempotencia y retención.

## Estado persistente en Cotizaciones (M3.1.1)

En `Seguimiento → Cotizaciones`, la aplicación consulta `GET /api/v1/reservations/{reservation}/demo-checkout` cuando la solicitud tiene una reserva comercial. La respuesta conserva `quote_id`, `reservation_status` y `selection_verified` del mismo registro B3.2; la app solo muestra el estado junto a la cotización exacta (`quote_id`). Se consulta nuevamente al volver a la pantalla y mediante «Actualizar cotizaciones», con una devolución de foco estable para evitar ciclos de recarga.

- `card` + `test_approved` + `selection_verified=true` + reserva `confirmed`/`completed` ⇒ **Pagado (prueba)**.
- Tarjeta aprobada mientras solo hay `held` ⇒ **Tarjeta aprobada (prueba) · falta confirmar reserva**.
- `cash` + `awaiting_cash` verificado ⇒ **Efectivo pendiente** (aunque la reserva esté confirmada).
- `cash` + `cash_received` verificado ⇒ **Efectivo recibido (prueba)**.
- Tarjeta rechazada o fallo temporal ⇒ nunca se indica pagado.
- Cotizaciones no vinculadas, API 404 fuera del laboratorio, y respuestas no verificadas ⇒ nunca se declara `Pagado (prueba)`.

Para comprobar el cambio sobre una reserva **ya confirmada** sin perder su estado, conservar el proceso B3.2 de Laravel y su SQLite temporal, hacer `git pull --ff-only` en las **mismas ramas** desde otras terminales, reiniciar Expo y regresar a Cotizaciones. No ejecutar el lanzador otra vez para esa misma reserva: eso crea una base sintética NUEVA.

## M3.1.2 — Ver comprobante interno y estado tras cancelación

Desde «Seguimiento → Cotizaciones → Importe acordado», al existir un método de prueba verificado para la cotización exacta, aparece «Ver comprobante interno de prueba». El comprobante desplegable muestra: reserva, método ficticio, referencia TK-TEST, fecha de selección (UTC convertida a la hora local en la app), importe y desglose incluido. Para efectivo pendiente muestra una advertencia de que aún no fue recibido. En ningún caso es un comprobante bancario, fiscal o una operación monetaria real.

Se respetan los estados de la reserva: tarjeta aprobada + reserva confirmada = «Pagado (prueba)»; si se cancela después, el intento se conserva como **«Reserva cancelada · aprobación de prueba histórica»**, sin presumir devolución ni reembolso. El efectivo no recibido y la reserva cancelada nunca se presentan como pagados.

Los datos proceden del nuevo GET privado de Laravel; el componente no persiste tarjetas ni puede modificar el estado de pagos. Verificar visualmente con una fixture B3.2 que ya tenga una operación, SIN volver a ejecutar el generador de SQLite.
